# SunoMaker — working notes

Wails v2 desktop app: Go backend, React 18 + TypeScript + Tailwind v4 frontend,
one binary for Windows/macOS/Linux. See README.md for what exists and how to run
it; this file is the house style.

## Verifying a change

```bash
go vet ./... && go test ./...   # backend
cd frontend && npm run build    # tsc + vite; tsc is strict, unused locals fail
wails build                     # the whole thing, including bindings
```

Bindings in `frontend/wailsjs/` are regenerated by `wails build` (or
`wails generate module`). After adding an exported method to `App`, regenerate
before the frontend can call it.

## Backend

- The app is `package app` in `internal/app`, one file per domain. The root
  holds only `main.go`, which calls `app.Main()`; keep it that way (#99).
- Code that needs nothing from `App` or `Store` gets a package of its own under
  `internal/` (`platform` for per-OS helpers, `audio` for audio files). Files
  that declare `App` or `Store` methods stay in `internal/app`: Go keeps a
  type's methods in its own package.
- Embedded files are embedded by a package in their own folder, since
  `go:embed` cannot reach up: `frontend.Dist`, `skills.Files`,
  `chromeextension.Files`.
- `store.go` owns the connection, the schema and settings. Domain files own
  their own table's SQL, as `*Store` methods below the types they populate.
- Bindings are methods on `App`. They validate, fill defaults, and return the
  **stored** record so the caller never has to re-fetch to learn what it made.
- `a.store` may be nil. Reads answer empty, writes return `errNoStore`.
- Slices returned to the frontend are `[]T{}`, never nil — the bindings marshal
  nil as `null` and every page would need to guard for it.
- New ids come from `newID(prefix)`, new timestamps from `nowStamp()`.
- After a write, report a scope with `s.changed(...)` so open pages refresh.
- Tests build an app with `newTestApp(t)`, which is backed by a temp-dir
  database and a temp music folder. Never touch the real `~/.sunomaker`, and
  never write into the producer's real music library.

## Frontend

- Colours come only from the semantic tokens in `style.css`. If a view needs a
  colour that is not there, add a token with **both** theme values and the
  contrast reasoning — do not reach for a Tailwind palette class.
- Shared shell and form pieces live in `components/`; a view that needs an
  input uses `TextField`/`TextAreaField`/`SelectField` rather than styling its
  own.
- Data that more than one view reads goes in a provider (see
  `artists/ArtistsProvider.tsx`), not in each view's own `useState`.
- Views subscribe to `useDataChanged([...scopes], reload)` so they pick up
  background writes — from MCP, from the bridge, from a sweep.
- Routing is App.tsx's history stack, not a router. Adding a section means: a
  `ViewId`, an entry in `PRIMARY_NAV` and `ROUTE_TITLES`, a `SECTION_OF` entry
  so the rail stays lit, and a branch in the content region.
- Errors get rendered, not logged: `toMessage(err)` and a `text-danger` line.

## The three long-running rules

**One report, one issue, one commit.** The bug queue is the repository's issue
list. Claim before you start; a report is not done until its fix is on `main`.

**Nothing about a tracker may fail the work.** GitHub and Jax are both reached
best-effort. A report refused because a tracker was closed is a report lost.

**The interview converses; a separate pass extracts.** Asking a model to hold a
conversation and emit JSON in the same breath is how you get a conversation with
a JSON block in the middle of it.
